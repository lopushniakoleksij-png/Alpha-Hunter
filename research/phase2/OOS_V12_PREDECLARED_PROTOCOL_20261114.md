# Phase 2 Scientific Validation V1.2 — OOS market-regime test protocol (LOCKED)

**Frozen 2026-11-14 BEFORE inspecting OOS signal outcomes or prospective test-day candle paths.** One deliberately bounded read-only historical experiment. V1.0/V1.1 evidence and certificates remain immutable. Draft research branch only, no production writes, real trading, deployment, filter changes, money spent or broad backfill.

## Experimental question

Does the V1.1 as-of, first-complete-per-symbol selection rule identify potential returns across *three previously untested historical market days* representing **rising**, **falling**, and **sideways** conditions? Are **original** engine gate states (`rr_minimum_met`, `participation_confirmed`, `momentum_confirmed`) associated with different hypothetical outcomes? This does not estimate the causal effect of changing any filter.

## Locked source universe and test-date selection

- Target symbols **BTCUSDT, ETHUSDT, SOLUSDT**, Bitget **USDT-FUTURES 1H market candles**. Use exact existing Supabase signal rows; no synthetic signals or real orders.
- Eligible OOS candidate day range: **2026-10-20 through 2026-11-06 inclusive**, UTC days, omitting the already examined 8 Nov pilot and any later dates. Prior daily scanner-coverage metadata have been inspected: every day in the range has records for all three symbols. **Actual signal outcomes, candidate-specific returns and test-day candles have not been examined as part of this V1.2 selection.**
- To avoid cherry-picking by subsequent performance, assign *market regime as of the beginning of each UTC day* using **BTCUSDT's immediately preceding completed 1Dutc candle**: `(close_previous_day / close_two_days_before - 1)*100`. **RISING** if > +1.00%, **FALLING** if < −1.00%, otherwise **SIDEWAYS** (including exactly ±1%). Only historical price candles completed strictly before the test day can determine the category. A prior-close trend label does not guarantee the following day trends in the same direction.
- For each regime, scan days **chronologically** and select the **earliest** day for which each of the three symbols has at least one complete, directionally valid, as-of signal available under the V1.1 rule. This selection requirement uses input visibility/geometry only, never future TP/SL, return or outcome.
- Select **exactly one UTC day per regime**. If a regime lacks a qualifying day (or reliable as-of candle/record evidence), classify **MISSING REGIME** and stop instead of replacing it with an attractive day. OOS 24h evaluation must fit in a validated 48h candle window. No further sample expansion without separate approval.

## Locked setup and outcome criteria

1. For each symbol/date, select the **earliest** signal in that day's records with direction SHORT/LONG, `TP < EP < SL` (SHORT) or `SL < EP < TP` (LONG), all strictly finite/positive, and `created_at` no later than the next full hourly bar. Earliest tie: `signal_id` lexicographic. **Do not use `trade_permission` as a selector**: passing/failing filter status must be retained for analysis. Include signals if permission is false; no action allowed.
2. Once a symbol candidate is selected, suppress all subsequent overlapping signals in that symbol for the day (24h calendar, one candidate per symbol per day); do not replace failed/ambiguous setups.
3. Evaluate only 24 consecutive **closed** 1H OHLC bars starting at the first full bar after detection. Entry price touched only when `low <= EP <= high`; if entry and an exit level touch in the same hour, **AMBIGUOUS**. If first post-entry hour touches both TP and SL, **AMBIGUOUS**. `NO_ENTRY` if not touched, `OPEN_AT_HORIZON` if entered without exit, `TP_FIRST` or `SL_FIRST` only when distinct later-hour touch ordering is established. No assumed fill.
4. Market-state and filters read **only from the original signal's stored `payload.execution_setup.checks`** at its timestamp, not computed using future outcomes. `trade_permission` is a separate system-level field and cannot be used as proxy for a specific filter's success. Report `PASS`, `FAIL`, `MISSING` separately for each of `rr_minimum_met`, `participation_confirmed`, `momentum_confirmed`. If no PASS candidates in a filter, report **NOT COMPARABLE**, never fabricate a matched pass-rate.
5. Baseline fee **0.0006 per side** (published standard Bitget taker schedule) plus adverse slippage **0.0005 per side**; sensitivities 0 and 0.001 per side. Position size **1000 USDT of unleveraged reference notional per candidate**; both sides charged on adverse executed prices; no assumed maker fills. No fee on `NO_ENTRY`. P&L only for unambiguously touched TP/SL; ambiguous/open positions have **unrealized/unknown** P&L, not $0 win/loss.
6. Funding is excluded from net baseline; if bounded historical funding cash flows can be verified independently, display separately with timestamp/mark-notional assumptions. No invented £ conversion or compounding. Report nominal stop-risk, gross/net scenario expectancy per *resolved* hypothetical setup, unresolved counts, and max concurrent correlated positions; never represent scenario return as executed profit.
7. **Comparison caveat:** 3 regimes × at most 3 symbols = at most 9 symbol-level opportunities, only three independent *calendar episodes* at best. No significance test/Sharpe, validated win rate, filter causality, meaningful generalization or decision to loosen safeguards.
8. Data-quality hard gate: no candidate-specific future OHLC/return inspection before selecting days and candidates. Verify exact 1H UTC continuity, OHLC bounds, source exchange/product/granularity, raw SHA-256, as-of timestamps and duplicate signal IDs. Store new OOS evidence in a **new** private folder only; do not overwrite sealed V1.0 or V1.1 artifacts.
9. Results must separately label **EXPLORATORY READ-ONLY CALCULATION** until new OOS raw candle responses, exact signal snapshot and filter fields are privately archived and replay-certified. Historical-universe eligibility remains UNKNOWN / release NO-GO even for BTC/ETH/SOL without independent historical availability verification.
